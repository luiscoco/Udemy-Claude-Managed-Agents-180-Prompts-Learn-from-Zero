# Make every lab a practical exercise

For each lesson, run the prepared walkthrough once, then change something and predict the result before running it again.

## Your lesson record

Copy this checklist into your own notes:

- [ ] I can explain the lesson's concept in two sentences.
- [ ] I completed the guided exercise.
- [ ] I changed an input and predicted its effect.
- [ ] I inspected the handler responsible for that behavior.
- [ ] I explored a failure or boundary case where the lesson supports one.
- [ ] I can distinguish the classroom behavior from a live provider integration.
- [ ] I saved a short explanation or sanitised screenshot of what I learned.

## Extension challenges

| Stage | Try this |
| --- | --- |
| Foundations | Change the input document and explain how the analysis changes. |
| Sessions | Trace the state changes around interruption or continuation. |
| Tools | Add a validation rule and show both an accepted and rejected input. |
| Permissions | Explain why an action is blocked, then change the relevant control and rerun it. |
| Memory | Reproduce a conflict and document how the exercise resolves it. |
| Workflows | Draw the branch taken by one input and compare a different input. |
| Operations | Explain which metrics are fixtures and how you would collect real measurements. |
| Complete projects | Extend one local output and document the changed behavior. |

## Turn your work into portfolio evidence

For one selected project, write a short problem statement, show the application, explain your change and include verification results. Label simulated provider behavior clearly. Do not include API keys, personal documents or account identifiers in screenshots or shared repositories.
